# Documentation

1. Treat the implementation and approved project specifications as sources of truth; do not invent behavior.
2. Inspect existing docs and preserve terminology, structure, and language conventions.
3. Keep instructions executable and paths, commands, environment variables, and examples accurate.
4. Distinguish implemented behavior, planned behavior, assumptions, and unresolved decisions.
5. Update related docs when API contracts, schemas, configuration, or workflows change.
6. Never include real secrets, tokens, personal data, or production credentials.
7. Prefer concise examples over repeated prose.
8. Link to authoritative internal documents rather than duplicating long sections.
9. Mark uncertain or unverified deployment steps explicitly.
10. Do not rewrite unrelated documentation.
